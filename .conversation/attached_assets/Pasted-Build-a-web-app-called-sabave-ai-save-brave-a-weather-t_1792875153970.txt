Build a web app called "sabave.ai" (save + brave): a weather-triggered marketing automation module for "Orbyte", a shared business hub platform for Malaysian micro and small businesses (SMEs). When a weather signal (haze, or heavy rain/thunderstorm) is forecast for a business's location, sabave.ai automatically prepares 2-3 marketing campaign options in that business's own brand style. Staff edit a draft, the Owner approves it within a budget cap, the campaign is "published" to Facebook/Instagram through a MOCKED Meta connector, and every step is recorded in an append-only activity log.

The app must demonstrate one complete 5-step journey:
1. TRIGGER: a weather signal crosses its threshold (or a "Simulate" button is pressed)
2. CONNECTED DATA: the business's Brand Kit and the forecast are loaded
3. DECISION LOGIC: deterministic rules choose the campaign options and budgets; the LLM only summarises brand style and writes copy
4. HUMAN APPROVAL: only the Owner role can approve and publish (enforced on the server)
5. VISIBLE OUTCOME: a simulated publish result is shown and logged

==================================================
STACK AND CONSTRAINTS
==================================================
- Next.js 14 (App Router), TypeScript (strict), React 18, Tailwind CSS, Node 22. No UI kits beyond Tailwind.
- Must run and deploy on Replit. Dev: `next dev -H 0.0.0.0 -p 3000`. Production: `next build && next start -H 0.0.0.0 -p 3000`. Configure .replit for both.
- NO database. JSON seed files in /data plus an in-memory server store implemented as a singleton on globalThis (so it survives hot reloads). Uploaded images are stored in memory as base64 data URLs (max 2 MB each, PNG/JPEG/SVG/WebP only).
- External weather APIs (both free, no key). Use a 5-second timeout on each; on failure, use the bundled offline forecast and label it "offline data":
  * Air quality: https://air-quality-api.open-meteo.com/v1/air-quality?latitude={lat}&longitude={lon}&hourly=pm2_5&forecast_days=5&timezone=Asia%2FKuala_Lumpur
  * Weather: https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lon}&daily=precipitation_sum,precipitation_probability_max,weather_code&forecast_days=5&timezone=Asia%2FKuala_Lumpur
- LLM: DeepSeek, via its OpenAI-compatible Chat Completions API, server-side only.
  * POST {DEEPSEEK_BASE_URL}/chat/completions with the header "Authorization: Bearer {DEEPSEEK_API_KEY}".
  * Env vars from Replit Secrets: DEEPSEEK_API_KEY (required for AI features), DEEPSEEK_BASE_URL (default "https://api.deepseek.com"), DEEPSEEK_MODEL (optional override). Never send the key to the browser, never prefix it with NEXT_PUBLIC_, never log it, never hard-code it.
  * Model selection: use the latest DeepSeek Pro model. If DEEPSEEK_MODEL is set, use it. Otherwise call GET {DEEPSEEK_BASE_URL}/models once on first use (cache the result) and pick the newest model whose id contains "pro"; if none, fall back to "deepseek-chat". Log the chosen model id (not the key) to the server console.
  * Request JSON output with response_format { "type": "json_object" }, and include the word "JSON" plus an example schema in the system prompt. If the response contains reasoning content, ignore it and parse only the final message content. Validate the parsed JSON; on invalid JSON retry once, then fall back to a template.
  * Timeout of 30 seconds per call (Pro models can be slow); show a spinner in the UI.
  * DeepSeek is TEXT ONLY: never send images to it.
  * Every LLM call has a template/manual fallback so the journey never breaks.
  * The LLM NEVER decides budgets, which option is chosen, or whether to publish.
- Meta is MOCKED. No real Meta/Facebook/Instagram/WhatsApp/TikTok API calls, no real payments or ad spend. Label all publish results "simulated".
- Synthetic data only. Business-level data only, no customer personal data (Malaysian PDPA).
- Root files: LICENSE (full Apache 2.0 text), .env.example (DEEPSEEK_API_KEY=, DEEPSEEK_BASE_URL=, DEEPSEEK_MODEL= with empty values), .gitignore (node_modules, .next, .env*, but keep .env.example), README.md. Never commit secrets.
- Login and roles are simulated; no auth library.

==================================================
MODULES AND RESPONSIBILITIES
==================================================
users.ts: two simulated users, { id: "u1", name: "Aisyah", role: "staff" } and { id: "u2", name: "Mr. Tan", role: "owner" }.

store.ts: globalThis singleton holding businesses (loaded from JSON on first access), forecasts, alerts, drafts and logs, with simple get/set helpers.

activityLog.ts: append(entry) and list(businessId?). Append-only: no update or delete. Actions: FORECAST_CHECKED, SIGNAL_SIMULATED, ALERT_TRIGGERED, OPTION_SELECTED, DRAFT_GENERATED, DRAFT_EDITED, NEVER_SAY_BLOCKED, SUBMITTED_FOR_APPROVAL, APPROVED, REJECTED, PUBLISHED, BUDGET_BLOCKED, ACTION_DENIED, BRAND_KIT_CREATED, BRAND_KIT_UPDATED, POSTER_ANALYZED, WEBSITE_ANALYZED, ANALYSIS_FALLBACK, AI_FALLBACK.

signals/signal.ts: a pluggable interface so new signals (e.g. heatwave) can be added just by registering a new file:
  interface WeatherSignal { id: SignalId; label: string; icon: string; fetchForecast(b: Business): Promise<SignalForecast>; simulate(b: Business): SignalForecast; triggerLevel: number }
signals/registry.ts: exports all registered signals.

signals/hazeSignal.ts: Open-Meteo pm2_5, grouped into daily max values (µg/m³). Levels: 0 Good (<35), 1 Moderate (35-55), 2 Unhealthy (55-150), 3 Very Unhealthy (>150). triggerLevel = 2. simulate() returns the daily values [45, 90, 165, 120, 50].

signals/rainSignal.ts: Open-Meteo daily precipitation_sum (mm) and weather_code. Levels: 0 Light (<10 mm), 1 Moderate (10-30), 2 Heavy (30-60, or any thunderstorm code 95-99), 3 Very Heavy (>60). detail = "Thunderstorm" when the code is 95-99. triggerLevel = 2. simulate() returns [5, 40 + thunderstorm, 75 + thunderstorm, 35, 8].

triggerEngine.ts: evaluate(forecast, business): if any day's level >= triggerLevel, create a WeatherAlert (affected dates, peak, daysAhead = days from today to the first triggering day). Don't create a duplicate open alert for the same business + signal + dates. Log ALERT_TRIGGERED.

campaignRules.ts (deterministic and explainable, NO AI): an option catalogue per signal, filtered by business type and Brand Kit:
  HAZE: "delivery_push" (only if delivery = true), "stay_home_bundle" (cafe: family meal/drinks pack; laundromat: pickup + wash-and-fold; retail: online order + click-and-collect), "clean_air_walk_in" ("We're open, comfortable indoor air" with a small in-store offer).
  RAIN: "rainy_day_delivery" (only if delivery = true), "shelter_comfort" ("Come shelter with us" comfort offer, e.g. hot drinks, express dry), "rain_check_voucher" (a voucher redeemable on the next dry day).
  - Return 2-3 options. offer uses the business's real products and prices (e.g. "RM2 off Nasi Lemak Ayam (RM8 -> RM6)").
  - suggestedBudgetRM = cap × (0.3 for level 2, 0.5 for level 3) × min(1, triggeringDays / 3), rounded to the nearest RM10, minimum RM20, never above the cap.
  - reason is a plain sentence built from data, e.g. "Very Unhealthy haze is forecast in Shah Alam on 28-30 Oct. Last time bad weather hit, your sales dropped 22%. You deliver, so a delivery push keeps orders coming while walk-ins fall."

neverSay.ts: findViolations(text, neverSay[]): case-insensitive whole-word/phrase match across headline, captions, hashtags and CTA. Always also blocks health/medical claims (e.g. "cure", "protects your lungs", "prevents illness", "kills germs").

llm.ts (DeepSeek client): generateJSON({ systemPrompt, userPrompt, exampleSchema }) -> parsed object or throws. Handles model selection and caching, response_format json_object, the 30-second timeout, one retry on invalid JSON, and ignoring reasoning content. If DEEPSEEK_API_KEY is missing, it throws immediately so callers fall back. Also export getActiveModel() for UI badges.

copyGenerator.ts: generateCopy(business, alert, option): builds the prompt from business-level fields only (name, type, city, products, target customers, ethos, tone chips, posterStyleSummary, websiteVoiceSummary, language, neverSay) plus the signal, level, dates and option. The prompt asks for JSON { headline (≤ 8 words), caption_bm, caption_en (each ≤ 60 words, natural Malaysian tone, matches the brand voice), hashtags (3-6), cta, rationale (1 sentence) }, with no health/medical claims and avoiding every neverSay term. If the result contains violations, retry once with the violations listed; if it still fails, use the template copy and log NEVER_SAY_BLOCKED. On any error, use the template copy and log AI_FALLBACK. Always return both captions; the UI highlights the preferred language. templateCopy() builds a decent caption from the option, offer, business name and tone. source = "ai" (with the model id) or "template".

brandAnalyzer.ts:
  - analyzePoster({ colours, description, toneChips }): colours come from client-side extraction of the uploaded past poster; description is the owner's short description of it. DeepSeek returns JSON { layout, typographyStyle, tone, summary }. Fallback (no AI): a summary built from the colours, chips and description; log ANALYSIS_FALLBACK.
  - analyzeWebsite(url): server fetch with a 6-second timeout, a browser-like User-Agent, http(s) only, max 1 MB, blocking localhost/private IP ranges; extract the title, meta description and visible text (strip script/style tags, first 4000 characters); DeepSeek returns JSON { voiceSummary, keyThemes: string[], suggestedTone: string[] }. Fallback: return { fallback: true } and the UI uses the ethos text.

colorExtract.ts (client-side): draw an uploaded image on a canvas, sample pixels, ignore near-white, near-black and transparent pixels, bucket the colours, and return the top 3-5 as hex values. Used for both the logo (brand colours, editable with colour inputs) and the past poster (posterColours).

approvalService.ts (enforced on the SERVER):
  - Staff: create and edit drafts (copy, offer, budget, channels) and submit (draft -> pending_approval).
  - Owner: everything staff can do, plus approve (pending_approval -> published, which calls metaConnector) or reject (-> rejected, reason required).
  - Budget must be within RM0 and the cap; if it's over, return a 400 error and log BUDGET_BLOCKED.
  - Submit and approve both run neverSay on the current copy; if there's a violation, return a 400 error listing the terms and log NEVER_SAY_BLOCKED.
  - A wrong role returns 403 and logs ACTION_DENIED.
  - Every transition is appended to draft.history and the activity log.

metaConnector.ts:
  interface SocialConnector { publishPost(draft, business): Promise<PublishResult>; createAd(draft, business, budgetRM): Promise<{ adId: string }> }
  class MockMetaConnector implements SocialConnector: waits ~800ms; returns fake IDs like "fb_post_" + 6 random digits, "ig_post_" + 6 digits and "ad_" + 6 digits, with status "published (simulated)". Only Facebook/Instagram are "published"; WhatsApp/TikTok are shown as "coming soon".
  getConnector() factory, with a comment explaining it is designed as a reusable Orbyte connector that any Orbyte module can call, and that a real Meta Graph API connector can be swapped in later.

==================================================
API ROUTES
==================================================
The client sends the simulated user in the header "x-user-id" (u1 or u2). The server resolves the role from users.ts and never trusts a role sent by the client.
- GET  /api/businesses -> Business[] (summary)          | POST /api/businesses (BrandKit form) -> Business
- GET  /api/businesses/[id] -> Business                  | PATCH /api/businesses/[id] -> updated Business
- GET  /api/forecast?businessId=&signalId= -> SignalForecast
- POST /api/trigger { businessId, signalId, simulate?: boolean } -> { forecast, alert | null, options: CampaignOption[] }
- POST /api/generate { businessId, alertId, optionId, useAI?: boolean } -> CampaignDraft (status "draft", budget = suggested)
- PATCH /api/drafts { draftId, copy?, offer?, budgetRM?, channels?, action?: "submit" } -> CampaignDraft
- POST /api/approve { draftId, decision: "approve"|"reject", budgetRM?, reason? } -> CampaignDraft (owner only)
- POST /api/brand/analyze-poster { colours, description, toneChips } -> analysis | { fallback: true, summary }
- POST /api/brand/analyze-website { url } -> analysis | { fallback: true }
- GET  /api/log?businessId= -> LogEntry[] newest first
- GET  /api/stats?businessId= -> { campaignsLaunched, avgDaysAhead, minutesSaved } where minutesSaved = campaignsLaunched × 85 (assumes ~90 min manually vs ~5 min with sabave.ai)
